# fish 的带说明参数联想是怎么做的，keygrp 照做成本几何？

- **Status:** Research note（非 ADR）。问题：fish 里很多命令的 tab 补全每个参数都有说明，看着像直接读的 `--help` 输出——这是怎么实现的？keygrp 要实现同样效果，成本高吗？
- **Verdict:** fish **并没有**「运行时解析 `--help` 输出」的通用机制；`__fish_parse_help` 这个函数**不存在**于任何 fish 版本。带说明的补全来自两条主链路：**（1）手写补全脚本**（fish 自带约 1000 个，含 jq/git 等），**（2）man page 补全**（`fish_update_completions` → `create_manpage_completions.py`，批量离线生成，非按需）。keygrp 是**无框架 DIY** 的 `__complete` 协议，目前候选不带说明；实现带说明补全的**成本很低**——fish 端脚本几乎不用改（已验证），主要工作是把 `internal/completion` 的候选表带上描述即可（约一天内的改动量）。

---

## 1. 背景

用户在 fish 里观察到：很多命令在 tab 补全时，每个参数都带一行说明（如 `git --bare  Treat the repository as a bare repository`），像是程序直接读了自己的 `--help` 输出。想知道这是否是「全自动」的、keygrp 要实现同样效果要花多大成本。

## 2. 一个必须澄清的误区：`__fish_parse_help` 不存在

研究问题里假设存在 `share/functions/__fish_parse_help.fish`。经核实：

- **本机 fish 4.8.1**（`/opt/homebrew/Cellar/fish/4.8.1`）：`type -a __fish_parse_help` → `Could not find`；`source embedded:functions/__fish_parse_help.fish` → `No such file or directory`。fish 4.x 把自带函数以 `embedded:functions/...` 形式打进二进制，不存在该文件。
- **fish 官方仓库**（`fish-shell/fish-shell`）在 4.8.1 / 3.7.1 / 3.1.2 / 2.7.1 / master 的 git tree 里**都搜不到 `__fish_parse_help`**（GitHub API tree 递归检索 + 直接取 raw 文件均 404）。
- fish 3.x/2.x 里名字最接近的是 **`__fish_print_help`**（`share/functions/__fish_print_help.fish`），它做的事是**渲染 fish 自己的 man page 文本**（供 `builtin --help` / `help` 显示），**不是**补全生成器，更不是通用 `--help` 解析器。fish 4.8.1 中 `type -a __fish_print_help` → `Defined in embedded:functions/__fish_print_help.fish @ line 2`。

结论：用户（以及研究问题）记忆里的 `__fish_parse_help` 是个不存在的函数。fish 没有「对任意命令跑 `--help` 并解析成补全」的能力。

## 3. fish 带说明补全的真正机制

### 3.1 机制一（主）：手写补全脚本，fish 自带约 1000 个

fish 源码仓库 `share/completions/` 下随发行版自带约 1000 个手写补全文件（fish 4.8.1 tree 统计）。每个文件就是用 `complete` 内置命令给某个命令注册候选 + 描述：

```fish
# share/completions/jq.fish（fish 4.8.1 源码，1819 字节）
complete -c jq -l compact-output -s c -d 'Don\'t pretty-print JSON'
complete -c jq -l arg -x -d 'Set variable'
...
```

- 语法：`complete -c <cmd> -l <long> / -s <short> -d '<描述>'`。`-d` 就是展示在候选右侧的说明。
- 这正是用户看到 git 补全的来源之一：fish 自带 `share/completions/git.fish`（4.8.1，3046 行），用 `complete -c git -l bare -d '...'` 等逐条注册。
- 本机验证：`complete -C "jq --"` 显示的 `--arg Set variable`、`--compact-output Don't pretty-print JSON` 与 `share/completions/jq.fish` 逐字一致——即来自这份手写脚本，而非 man page 生成（本机 `~/.cache/fish/generated_completions/` 里根本没有 jq.fish）。

### 3.2 机制二：man page 补全（`fish_update_completions` → `create_manpage_completions.py`）

对没有手写补全的很多命令，fish 提供从 **man page** 离线生成补全文件的工具：

- 入口是 fish 函数 **`fish_update_completions`**（fish 4.8.1 内置：`embedded:functions/fish_update_completions.fish @ line 1`）。它调用：
  ```fish
  status get-file tools/create_manpage_completions.py |
      ... $python -B - --manpath --directory=$__fish_cache_dir/generated_completions ...
  ```
  （源码：`/tmp/fish-shell-4.8.1/share/functions/fish_update_completions.fish:23`）
- 真正干活的是 **`share/tools/create_manpage_completions.py`**（2012 年加入，官方文档 `fishshell.com/docs/current/cmds/fish_update_completions.html`：*"parses manual pages installed on the system, and attempts to create completion files in the fish configuration directory"*）。它把 man page 的 roff 解析成 `complete -c cmd -l opt -d '描述'` 行。
- **产物位置**：fish 4.x 写到 `$__fish_cache_dir/generated_completions/`（本机 `$__fish_cache_dir=/Users/chi/.cache/fish`）。本机该目录有 **940 个文件、时间戳全部相同（2026-03-01 23:45）**，说明是一次批量 `fish_update_completions` 跑出来的。例如：
  ```fish
  # /Users/chi/.cache/fish/generated_completions/envsubst.fish
  # envsubst
  # Autogenerated from man page /opt/homebrew/share/man/man1/envsubst.1
  complete -c envsubst -s v -l variables -d 'output the variables occurring in SHELL-FORMAT ...'
  ```
  它给 envsubst 提供了带说明的 `--help/--version/--variables` 补全，而 fish 并没有手写 envsubst 补全——这正是「看着像读了 --help」的真相：**对 GNU 工具，man page 里就是 `--help` 同样的选项表**，fish 读的是 man page。

### 3.3 fish **没有**「按需（每次 TAB）自动生成」的机制

这是研究问题里「全自动」的关键答案：

- fish 4.8.1 的 Rust 源码 `src/` 里**不存在** `manpage_completions` 之类的模块（全树 grep，仅 `share/functions/` 与 `share/tools/` 里出现 manpage 字样）。fish 3.7.1 的 C++ 源码也没有（`src/` 下只有 `complete.cpp`，无 manpage_completions.cpp，且从未调用 `fish_update_completions`）。
- `src/autoload.rs:397-413` 只是把 `generated_completions` 目录当作普通补全目录**按优先级加载**，不负责生成。
- 本机实测：`cloudflared` 有 man page（`/opt/homebrew/share/man/man1/cloudflared.1`，2026-07-22 版本，晚于那次批量生成），且 fish 没有手写它的补全，结果 `fish -i -c 'complete -C "cloudflared --"'` **返回空**——没有任何按需生成。
- 因此「覆盖全」依赖两件事：fish 自带的 ~1000 个手写脚本 **+** 用户（或包管理器 post-install）跑过一次 `fish_update_completions`。新装的命令若两者都不覆盖，fish 只兜底到默认的文件补全。

### 3.4 机制三：`complete -a` 命令替换 + TAB 分隔描述（动态候选）

fish 的 `complete -a` 除了接字面列表，还可以接**命令替换**，输出里 **tab 之后的部分被当作描述**：

> "Each line of output is used as a separate candidate, and anything after a tab is taken as the description."（`fishshell.com/docs/current/completions.html`，"Writing your own completions" 章）

官方示例：
```fish
complete -c timedatectl -n "__fish_seen_subcommand_from set-timezone" \
    -a "(timedatectl list-timezones)"
```
即：补全脚本可以在运行时**调用命令本身**来枚举候选（很多工具用 `cmd <sub> <TAB>` 输出 `候选\t描述` 供 fish 消费）。这是最接近「运行时读程序输出」的机制，但它仍由**手写的补全脚本**驱动，且调用的是命令的子命令/专用输出接口，**不是**通用 `--help` 解析。

### 3.5 机制四：`complete -C` 与通用兜底

- **`complete -C "cmd args"`** 是 fish 内置：给定命令行，打印它应当得到的补全。它不生成新补全，只是「查询已注册补全」的入口（keygrp 的 fish 脚本正用它做目标程序的委托，见 §5）。文档：`fishshell.com/docs/current/cmds/complete.html`。
- **通用兜底**：当某命令没有任何补全脚本、也没有 man page 生成文件时，fish 只回落到**默认文件补全**（这正是 `complete -C "jq "` 在非交互下返回当前目录文件列表的原因）。不存在 `__fish_complete_external` 之类的「通用外部补全」函数——本机 `type -a __fish_complete_external` → `Could not find`。

## 4. 是「自动」还是「每命令手写」？

| 机制 | 谁在写 | 是否自动 | 覆盖 |
|---|---|---|---|
| 手写补全脚本（`share/completions/`） | fish 上游 + 各软件包 vendor | 随 fish/软件安装 | ~1000 个常用命令，质量最好 |
| man page 生成（`fish_update_completions`） | fish 的 Python 工具 | 需要跑一次批量命令（非按需） | 有 man page 的所有命令，质量参差（roff 解析常串行/截断） |
| `complete -a` 命令替换 | 手写脚本 | 每次 TAB 执行命令 | 工具自己提供候选接口时 |

**关键结论**：不是「全自动」，也**不是**「解析 --help」。用户要为一个新命令获得带说明补全，必须有人（fish 上游、软件包、或该命令自己）写一份 `complete -c ... -d ...` 脚本，或者该命令有 man page 且用户跑过 `fish_update_completions`。fish 能「看着很自动」只是因为：自带的 ~1000 个脚本 + 用户机器上那次批量 man page 生成，恰好把常用命令覆盖得七七八八。

## 5. keygrp 现状

### 5.1 项目概况

- Go 1.26 CLI（`go.mod`：仅 `pelletier/go-toml/v2`、`zalando/go-keyring`、`golang.org/x/term`），把 OS keychain 里的密钥按 profile 注入目标命令后 `exec(2)` 交棒（`docs/adr/0001-keygrp-design.md`）。
- 用法：`keygrp <profile> <program> [args...]`、`keygrp secret set|get|delete|list|export|import`、`keygrp check`、`keygrp init`、`keygrp completion <shell>`。

### 5.2 补全架构：无框架，DIY `__complete` 协议

- **没有 CLI 框架**（无 cobra/urfave）。`main.go` 用 `parseArgs` 手写解析参数（`main.go:126-268`）；`docs/adr/0002-shell-completion-and-init.md:10-14` 明确记录「cobra 被考虑后拒绝」。
- 补全分两层：
  - **`keygrp __complete -- <words...>`**（隐藏协议，`main.go:669-691`）是「协议大脑」，返回纯候选行，或指令行（`__directive:command` / `__directive:delegate` / `__directive:file`），见 `internal/completion/completion.go:18-22`。
  - **每 shell 一个薄脚本**（`internal/completion/scripts.go`）：fish 脚本 `complete -c keygrp -f -a '(__keygrp_complete)'`，拿到 `__complete` 输出后：指令交给 shell 原生能力（命令名补全、目标程序委托 `complete -C`、文件路径补全），普通候选 `printf '%s\n' $out` 直接打印（`scripts.go:58-92`）。
- 候选内容：子命令、flag、profile 名、secret ref、文件路径——全部是**纯字符串，无描述**（`completion.go` 的 `frontCandidates`/`secretResult` 等）。

### 5.3 框架「是否原生支持带描述补全」

该问题对 keygrp 不适用——它**没有框架**。若对照 cobra（ADR-0002 拒绝过的那款）：cobra 官方文档确认其生成脚本支持描述（有 `--no-descriptions` flag、`CompletionOptions.DisableDescriptions`），描述来自代码里命令的 `Short`/`Usage` 和 `ValidArgsFunction` 的返回值（`candidate\tdescription` 格式），**同样不是运行时解析 `--help`**。

## 6. 成本评估与方案对比

### 方案 A：引入 CLI 框架，用其自带补全能力

- 成本：**高**。keygrp 是 0 依赖的手写解析 + 自研 `__complete`（已评审、已测，`main_test.go` + `completion_test.go`）。换 cobra 等于重写 `parseArgs`/dispatch 全套，只为补全描述，收益不成比例。ADR-0002 已明确拒绝该方向。
- 价值：低。

### 方案 B（推荐）：保持 DIY 协议，给候选带上描述

核心改动只有一个：让 `__complete` 输出的候选行变成 **`候选<TAB>描述`**。fish 原生把 tab 后内容当描述，**已验证 keygrp 现有 fish 脚本零改动即可渲染描述**（用与 `scripts.go:58-92` 相同模式的 mock 实测：`complete -C "kgx "` 正确显示 `set\tStore a secret` 等）。

- **Go 端**（`internal/completion/completion.go`）：把静态候选表（子命令 `secret/check/init/completion`、flag `--help/--verbose/--profile/--shell/--stdin/--reveal/--skip-existing`、secret 操作 `set/get/delete/list/export/import`，约 20 个条目）改成「候选+描述」二元组；动态值（profile 名、secret ref）可挂通用标签（`profile` / `secret ref`）或留空。数据全在一处，**单一事实来源**。
- **fish 脚本**：无需改动（`printf '%s\n' $out` 原样透传 tab；`complete -a` 解析）。
- **zsh 脚本**：需小改。现在 `compadd -a out`（`scripts.go:126`）会把 `候选:描述` 整体当候选，需换成 `_describe`（cobra 同款做法）或把描述拆成独立数组 `compadd -d descs -- cands`。
- **bash 脚本**：需小改。`COMPREPLY` 用 `候选<TAB>描述` 约定（readline 新版支持菜单里显示描述），把描述拼进去；或继续只补候选、描述留空。
- **测试**：`completion_test.go` / `scripts_test.go` 同步断言描述输出。
- **开发量**：约 1 天（Go 端半天 + zsh/bash 脚本适配半天 + 测试）。**维护成本**：低——描述随候选表走，命令结构变更时顺带改，无二次维护面。
- **对用户的价值**：高——现在 `keygrp <TAB>`、`keygrp secret <TAB>` 只有光秃秃的词，加了描述后与 fish 里 git/gh 的体验一致，可发现性明显提升。

### 方案 C：像 fish 那样（按研究问题原假设）运行时解析 `--help`

- 先纠正前提：**fish 本身并不这么干**（§3.3），所以这不是「照 fish 做」。
- 即使做：keygrp 的命令/flag 在代码里已知（`main.go:26-47` 的 `usageText` 就是现成 `--help`），运行时再解析自己输出的 usage 文本纯属多余且脆弱（换行/缩进/版本差异都会破坏解析）。**成本高、价值低**，不推荐。

### 附带选项：为 keygrp 写一个 man page

- 若 keygrp 提供 `man` 页（如 `docs/keygrp.1`），用户跑过 `fish_update_completions` 的机器会自动获得带说明的 keygrp 补全（走 §3.2 机制）。但描述来自 roff 解析，**质量不稳**（实测 envsubst 的描述里串进了 `.SS "Informative output:"` 这类 roff 残渣），且**依赖用户机器跑过批量生成**，不可控。可作方案 B 的补充，不能替代。

### 对比表

| 方案 | 开发量 | 维护成本 | 用户价值 | 是否「像 fish」 |
|---|---|---|---|---|
| A 换 CLI 框架 | 高（重写全部） | 中 | 低 | 不是（框架描述来自代码而非 help） |
| **B 协议加描述（推荐）** | **约 1 天** | **低** | **高** | **是（fish 的手写补全就是这么给描述的）** |
| C 运行时解析 --help | 中高 + 脆弱 | 高 | 低 | 否（fish 无此机制） |
| 附：写 man page | 低 | 低（但要同步文档） | 中（依赖用户跑过生成） | 是（走 fish 的 man page 生成链路） |

## 7. 结论

- **fish 的带说明补全** = 手写补全脚本（`complete -c ... -d ...`，fish 自带 ~1000 个）+ man page 批量生成（`fish_update_completions` → `create_manpage_completions.py`），外加 `complete -a` 命令替换（运行命令自己的接口，输出 `候选\t描述`）。**没有**「运行时解析 `--help`」的通用机制，`__fish_parse_help` 不存在。
- **keygrp 要实现「每个参数带说明」的联想，成本很低**：采用**方案 B**，把 `internal/completion` 的候选输出从纯字符串改成 `候选<TAB>描述`，fish 端零改动、zsh/bash 各改几行，总量约 1 天工作量。这也是与 fish 官方手写补全**同构**的做法。
- 不建议为此引入 CLI 框架（方案 A），也不必做运行时 `--help` 解析（方案 C）；若想锦上添花可补一个 man page（可选，非必需）。
